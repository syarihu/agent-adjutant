# 設定とランタイム詳細

agent-adjutant の高度な設定項目、コマンドテンプレート、環境変数、ターミナルバックエンド、セッションのライフサイクル管理について説明します。

コメント付きの完全な JSON スキーマについては [`config.example.json`](../config.example.json) を参照してください。

---

## 設定ファイルの配置と優先順位

設定ファイルの配置場所: `~/.config/adjutant/config.json`（`$XDG_CONFIG_HOME` および `$ADJUTANT_CONFIG` に対応）。

設定の解決順序（より具体的な指定が優先されます）:
1. リポジトリ個別設定（`repos["owner/name"]`）
2. リポジトリの既定設定（`defaults`）
3. `config.json` のトップレベル設定
4. 組み込みの既定値

未知のキーや不正な形式があっても設定の読み込みでエラー終了はせず、`adjutant config` で確認できる警告（`warnings`）を出力したうえで安全にフォールバックします。

---

## コマンドテンプレートとプレースホルダ

`config.json` に記述するコマンド群はテンプレートとして展開されます。プレースホルダは**あらかじめシェルクォートされた状態で**挿入されるため、テンプレート側で引用符を付ける必要はありません。

```jsonc
// プレースホルダをダブルクォートで囲まないでください
"terminal": {
  "spawn": "my-terminal --title {title} -- {command}"
}
```

### 長いコマンドラインの退避（ステージング）
展開後のコマンドラインが900バイトを超える場合（`agentEnv` で長い `PATH` を渡す場合など）、adjutant は内容をシステムの一時ディレクトリ（`TMPDIR`、未設定ならプラットフォームの既定）の `adjutant-spawn-*.sh` に書き出し、`sh <そのスクリプト>` を実行します。ターミナルに長い行を入力させると途中が欠けて別のコマンドとして実行されることがあるため、短い行で済ませてこれを防ぎます。なお `--dry-run` 時は中身を確認できるよう退避を行いません。

## 環境変数

- `ADJUTANT_CONFIG`: 独自の設定ファイルパスを指定します。`adj hub --tab` や `adj work` が開くタブへ自動で引き継がれます。
- `ADJUTANT_STATE_DIR`: 独自の状態保存ディレクトリを指定します（既定: `~/.local/state/adjutant`）。相対パスで渡された場合はメインチェックアウトを基準とした絶対パスに変換して渡されます。
- `ADJUTANT_HUB`: 対象の hub を指定します。`adj work` は起動した worktree に hub の識別子を書き込むため、worker からの報告は正しい hub へ確実に届きます。

## ターミナルバックエンド

### 1. 既定: 組み込み tmux バックエンド
`terminal.preset` を指定しない場合（または `"terminal": { "preset": "tmux" }` の場合）、tmux が標準バックエンドになります。tmux のインストールが必要で、入っていないと `adj work`、`adj hub --tab`、ボードからの hub 起動は、tmux が見つからないことを伝える1行のエラーで止まります。未知の `preset` の値は `adj config` の警告になり、tmux にフォールバックします。`terminal.spawn` テンプレートがある場合は、これまでどおり preset より優先されます。
- **バックグラウンドウィンドウ起動**: worker をデタッチウィンドウ（`tmux new-window -d`）として起動するため、作業中のフォーカスが奪われません。起動後の約3秒間プロセスを監視し、即座に終了した場合はスロットを解放してエラーを出力します。
- **ペインへの自動解決**: PID、TTY、プロセス階層を自動探索して tmux ペインを特定するため、専用のラッパースクリプトが不要です。
- **画面確認を伴う wake（入力通知）**: tmux ペインに入力する前に画面（`tmux capture-pane`）を確認します。エージェントが空の入力欄で待機しているときだけキーを送信します。質問、許可確認、メニュー、入力途中の文字がある場合は入力を保留し、デスクトップ通知へ切り替えます。
- **フォーカスと終了**: `adj focus` で対象のウィンドウとペインを選択し、`adj close` でウィンドウを終了します（`kill-window`）。
- **接続（アタッチ）**: `tmux attach -t adjutant` や iTerm2 経由の `tmux -CC attach -t adjutant` でいつでもセッションに接続できます。
- **CLI サブコマンド**: `adj tmux`（`pane`, `spawn`, `wake`, `focus`, `close`）から tmux セッションを直接確認・操作できます。
- **環境変数**: `$ADJUTANT_TMUX_SESSION`（既定の `"adjutant"` を上書き）および `$ADJUTANT_TMUX_SOCKET`（`tmux -L <socket>` に対応）に対応しています。

tmux の外で `adj hub` だけを実行した場合も、hub はそのターミナルで動きます。ただしボードからはそのターミナルを開けないため、tmux セッション内で hub を起動するには `adj hub --tab` を使ってください。

### 2. iTerm2（`terminal.preset: "iterm2"`、macOS）
AppleScript を使ってタブの作成、タイトルの設定、テキスト入力を行います。テンプレートに渡される `{pid}` と `{tty}` は OS の識別子（`ttys004` など）であり、ターミナルのペイン番号ではありません。macOS 以外でも指定は有効ですが、iTerm2 は macOS でしか動かないため `adj config` が警告を出します。

### iTerm2 既定からの移行
`terminal.preset` を指定していないとき、以前は iTerm2 が使われていました。アップグレード後は、新しい worker が tmux のウィンドウで開きます。従来どおりにするには次を設定します。

```json
{ "terminal": { "preset": "iterm2" } }
```

`terminal.spawn` だけを設定している場合、タブの起動はそのテンプレートのままですが、focus、close、wake は tmux バックエンドに向くようになります。iTerm2 のままにするには `"preset": "iterm2"` を追加してください。すでに動いているセッションは、記録されたバックエンドのまま扱われるため、close、focus、wake はこれまでどおり届きます。常駐サーバーは設定ファイルが変わると次のボードへのリクエストで読み直しますが、起動時のバイナリのまま動き続けるので、アップグレード後に `adj server restart` を実行してください。

## ランナーテンプレートとセッション再開

### 各種ランナー
- `agentRunner`: タスク worker を起動するコマンドテンプレート。
  - 既定値: `claude --session-id {sessionId} --permission-mode auto {settings} {prompt}`
- `hubRunner`: リポジトリ hub を起動するコマンドテンプレート。
  - 既定値: `claude -n {name} --session-id {sessionId} --permission-mode auto {settings} {prompt}`
- `reviewerRunner`: PR の読み手（AI 下読み）を起動するテンプレート。
  - 設定ファイルと MCP の読み込みを無効化し（`--setting-sources '' --strict-mcp-config --permission-mode dontAsk`）、読み取り専用の安全な環境で動作させます。
- `agentResumeRunner` / `hubResumeRunner`: `--resume` 指定時に既存の会話を再開するためのテンプレート。

### エージェントのモデル指定（`--model`）
- **CLI フラグ**: `adj work` / `adj worker` に `--model <MODEL>` を付けると、その worker セッションのモデルを指定できます。
- **`{model}` プレースホルダ**: worker のランナーテンプレート（`agentRunner`、`agentResumeRunner`）では、モデルを渡したい位置に `{model}` を書けます。値はシェル用にクォートして埋め込まれるため、テンプレート側でクォートしないでください。モデルを指定しなかったときは `{model}` を取り除きます。直前の単語がモデル指定オプション（`-m` や、`--` で始まって名前に `model` を含む `--model`、`--agent-model` 等）の場合、または `--*model*={model}` の形式の場合は、オプション語ごと取り除いて空の引数や二重の空白が残らないようにします。
- **`{model}` を含まない claude ランナー**: `claude` を起動し、自分では `--model` を渡していないランナー（既定のランナーを含む）には、`claude` の直後に `--model <MODEL>` を足します。モデルを受け取れないランナー（`{model}` を含まない claude 以外のランナーや、すでに `--model` を渡している claude のランナー）で `--model` を指定すると、起動前に拒否します。
- **使える文字**: ASCII の `A-Z a-z 0-9 . _ - : / @ [ ]` で 1〜128 文字、先頭は英数字（例: `opus`、`sonnet`、`claude-opus-5-5`、`sonnet[1m]`、`openai/gpt-5`）。
- **再開時の引き継ぎ**: 指定したモデルは `.claude/adjutant-session.json` に保存し、`adj work --resume` では同じモデルで再開します。`--resume` に `--model` を付けると、保存済みのモデルを置き換えます。`agentResumeRunner` が保存済みのモデルを受け取れないときは、モデルを渡さずに再開し、警告を表示します。

### セッションのライフサイクルと自動再開
- **自動再開の有効期間（`hubAutoResumeHours`）**: hub の終了からこの時間（既定: 3時間）以内であれば、素の `adj hub` を実行するだけで前回の会話を自動的に再開します。有効期間を過ぎている場合は空の会話で新しく立ち上がります。
- **話しかけられていない読み手を閉じる（`readerIdleMinutes`）**: 下読みを提出した PR の読み手（AI 下読み）に、この分数（既定: 60分）のあいだ誰も話しかけなかった場合、常駐のボードサーバーがそのセッションを閉じます。閉じるのはセッションだけで、下読み結果・下書き・レコードは残ります。話しかけられたかどうかは、読み手の agent-session の行の `updatedAt`（status が変わるたびに動く。ターンの開始と終了、権限の承認待ちに入るときと抜けるとき）で見ます。閉じるのは最後のターンが終わっているセッション（`idle`・`done`・`failed`）だけで、実行中や権限の承認待ちのセッション、status が無いか、このバージョンが知らない status のセッションは閉じません。agent-session の行が無い読み手（adjutant のフックを入れていない `reviewerRunner` など）も閉じません。ほかの閉じ方と同じく読み手の tmux ペインを閉じるので、tmux の外で動く読み手は開いたまま残り、ボードサーバーのログに理由が出ます。`0` で無効になります。
- **セッション ID の管理**: ランナーに `{sessionId}` を含めると、ID を `~/.local/state/adjutant/sessions/`（hub）または `.claude/adjutant-session.json`（worker）に保持し、次回以降の確実な再開に利用します。
- **生存監視**: 稼働中の hub は1分ごとおよび終了時にハートビートファイル（`sessions/<slug>.alive`）を更新します。これにより、予期せず終了したプロセスが稼働中と誤認されるのを防ぎます。

## デスクトップ通知

`notification` テンプレートで使えるプレースホルダ: `{title}`, `{message}`, `{nwo}`（リポジトリ名 `owner/name`）。

- **未設定のとき（既定）**: 次の順で、鳴らすのは1か所だけです。
  1. 90 秒以内にポーリングし、通知を出せるデスクトップアプリがあれば、アプリだけがネイティブ通知を鳴らします。
  2. なければ、90 秒以内にポーリングし、通知の許可があるブラウザのボード画面があれば、その画面だけが鳴らします。
  3. どちらもなければ、`terminal-notifier`（クリック時にターミナルをアクティブ化できる）が入っていればそれで鳴らします。入っていなければ鳴りません。`osascript` へのフォールバックはありません（macOS が Script Editor の通知として扱うため）。

  「開いている」かどうかはブラウザの通知の許可だけで決まり、確認待ちの設定には左右されません。アプリが開いているあいだ、ブラウザの画面は何も鳴らしません。

  待ちと gate も同じ順ですが、そのクライアントの確認待ちが ON であることも必要です。鳴らす側がボードを見ているサーバープロセスにポーリングしていれば、そのクライアントが自分で鳴らします。別のサーバープロセスに開いている場合（このボードは見えません）は、サーバーがその宛てに通知を1回だけ積みます。鳴らす側の確認待ちが OFF なら、待ちも gate もどこにも鳴りません。「開いている」かどうかは、画面がつながっているボードサーバーだけでなく、このマシンのすべてのボードサーバーの記録から読みます。macOS に 90 秒より長く止められたアプリのウィンドウ（隠れているときなど）は閉じているものとして扱うので、そのあいだは開いているブラウザの画面が鳴らすことがあります。

  どちらも開いていないとき、待ちや gate はあとでボードの TODO に残っていますが、`adjutant send` / `adjutant tell` や `adj notify` のメッセージは残りません。`terminal-notifier` が入っているときだけ表示されます。アプリや画面に向けて積んだ通知が約 100 秒以内に取られなかったとき（ウィンドウを閉じたなど）は、`terminal-notifier` が入っていればそれで鳴らし、無ければ捨てます。
- **コマンドを設定したとき**: これまでどおり実行され、`false` なら通知しません。どちらもアプリや画面が開いているかは見ません。ただし待ちと gate は、同じサーバーのボード画面が開いているあいだはその画面に任せます。
- **Linux での動作**: `"notification": "notify-send {title} {message}"` を設定してください。ボード画面が開いていれば、未設定の `notification` は画面に積まれます。
- **発火条件**:
  - `adjutant send` / `adjutant tell` による直接メッセージ
  - 数秒以上、権限プロンプトや質問への回答待ちになっているセッション
  - 新しく開いた gate
  - なお、`notification` が未設定のときは、開いているアプリかボードの画面が鳴らします（上記）。コマンドを設定しているときは、そのサーバーの Web ボードが開かれてポーリング中なら、画面側の通知が優先され、コマンド側は抑制されます。

## worker の PR を誰がマージするか（`merge`）

`merge` はリポジトリごと（または `defaults`）に設定します。

- `"person"`（既定）: worker が開いた PR は人がマージします。終わった worker は hub に worktree の片付けを頼み、その依頼は人の返事を待ちます。
- `"hub"`: hub がマージします。worker が PR の準備ができたと言うと（未対応の `must` の指摘がない、`verify` が通っている、レビュー bot への対応が済んでいる）、片付けの gate を開かずに `done` を送ります。hub は、PR が open で draft でなく、チェックがすべて通り、ベースに対して `CLEAN` で、`done` を送ったあとに何も足されていないときにマージします。マージはマージコミット（`gh pr merge --merge`）で、そのあと worktree を片付けます。hub が判断できないもの（レビューの返事待ち、GitHub が拒むマージ、30 分待ってもチェックが終わらない）は人に任せ、worker が直せるもの（CI の失敗、遅れて来たレビュー）は worker に差し戻します。

`merge` は hub 自身の設定から読み、worker が書いた内容では決まりません。ほかの値は `warnings` に出て、`"person"` として扱われます。

---

## 人なしでタスクを流す（`autopilot`）

`autopilot` はリポジトリごと（または `defaults`）に設定します。既定は `false` です。`true` にすると、hub がキューのタスクを、ボードの前に誰もいなくても、マージされた PR まで進めます。

やること:

- **`merge` の既定を `"hub"` にします。** 先に言及があったものが勝ちます。リポジトリ自身の `merge`、次にリポジトリの `autopilot`（`false` なら `defaults` の `merge`、なければ `"person"`）、次に `defaults` の `merge`、次に `defaults` の `autopilot`、どれもなければ `"person"` です。このため、`defaults` で `autopilot` を入れたうえで特定のリポジトリだけ切ることも、`merge: "person"` を残して hub に残りを任せることもできます。`adj config` には決まったあとの `merge` と `autopilot` が出ます。
- **Stop at の既定を `none` にします。** hub が Stop at を書く場面（読み取る board の依頼、起票する報告、タブでの何も指定のない依頼）が対象です。レコードにすでにある Stop at と、人が名指ししたものはそのままで、Jules に渡すタスクは `plan` のままです。
- **報告を起票してキューに入れます。** `## Scope` のない worker の報告は、起票だけでなくキューにも入ります。open な issue と明らかに同じバグなら、その issue へのコメントにします。キューが順に着手します（`maxWorkers` が必要です）。
- **開始確認を省きます。** 読み取りに未解決の点がない board の依頼が対象です。
- **進行中のタスクと重なるタスクを待たせます。** 着手の前に、hub は進行中のタスク（issue 本文と、相手 worker の plan の手順）と見比べます。重なっていれば `Waiting for task <key>: overlaps <area>` というメモを書き、`adj task next` はそのタスクを飛ばし、相手が done になるとメモを外します。相手のブランチに積むことはしません。

それでも人が止めるもの: `verify` の失敗、hub が自分で判断できないマージ、`issueCreate.command` の欠落や対話式のもの、別リポジトリ宛ての報告、`needs-user` や報告だけでは決まらない質問、worker からのタスク分割の提案、Jules の plan、`autoStart: false` のタスクの開始確認、未解決の点がある読み取り、既存の Jira チケットへの追記です。

`maxWorkers` のない `autopilot` は `warnings` に出ます。hub は空きがあるときにだけキューのタスクを始めるので、自分では始めません。同じ場所で `autopilot: true` と `merge: "person"` を並べた場合も出ます（`merge` が勝ちます）。`true` / `false` 以外の値は報告され、`false` として扱われます。登録のないリポジトリが autopilot になることはありません。

まだないもの: board は `autopilot` を表示も切り替えもしません（設定ファイルだけが入口です）。一時停止はありません。hub はトラッカーから新しい仕事を拾いません。親タスクの hub はリポジトリの設定を読むだけで、独自の設定を持ちません。
