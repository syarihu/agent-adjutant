---
description: 実装中に見つけた別件の不具合を、worktree から出ずに常駐 hub へ渡す
---

Report — いま立っている worktree から出ずに、**いまのタスクとは別の不具合**を hub
（`adj-hub` の常駐セッション）へ渡す。hub が起票と着手判断を引き受けるので、こちらは
渡したら自分の作業に戻る。

引数 `$ARGUMENTS` = 見つけたことの説明。省略されたら直前の会話から組み立てる。

## この3つが前提

- **自分で直さない。** いまのタスクの diff に無関係な修正が混ざると、レビューもリバートもできなくなる。
- **自分で起票もしない。** 重複判定・テンプレート・ラベル・ボード登録・着手判断は hub 側に
  1箇所にまとめてある。
- **返事を待たない。** 送ったら終わり。hub の返事は後から届く。

## Context — 最初に1回だけ集める

- `adjutant_hub_status`（引数なし。いまの worktree からリポジトリを解決する）。返るのは
  `repo` / `main` / `hubName` / `present`（hub が起動しているか）/ `waiting`（受信箱の残件数）。
  **hub 名を自分で組み立てない。** 名乗る側と探す側が同じ導出を通るから一致するのであって、
  規則を写した時点でずれる。
- `git rev-parse --show-toplevel` と `git branch --show-current`
- `.claude/task-brief.md` があれば先頭12行

## 手順

### 1. 事実を固める

`$ARGUMENTS` と直前の会話から、症状と該当箇所を確定する。**file:line を記憶や推測で書かない** —
1〜2箇所だけ実際に開いて確かめる。hub は別のブランチを見ているので、ここで外すと誰も直せない。

いまのタスクの範囲内かどうかも、ここで一度考える。範囲内なら報告ではなく普通に直す話。

### 2. 本文を組み立てる

```
## 症状
## 発見経路 / 再現手順
## 該当箇所        file:line（複数可）
## 想定原因        分かる範囲だけ。分からなければ「未調査」
## 今のタスクの範囲外である理由
## 親タスク        {task_id} {task_url}
## 報告元          {repo} / {branch} / このセッション名
```

- 親タスクは `.claude/task-brief.md` の「作業対象」行から。無ければブランチ名のキー
  (`{user}/ALPHA-957` → `ALPHA-957`) から引く。
- **30行以内。調査ログを貼らない。** hub が issue テンプレートに詰め直すので、ここは素材でいい。

### 3. ユーザーに見せて、確認を取る

**`AskUserQuestion` と同じターンに書いた本文はユーザーの画面に出ない。** 本文は Q1 の
「このまま投げる」オプションの `preview` に入れて、1回の呼び出しで見せながら聞く。本文が
`preview` に収まらないほど長いなら、それは30行を超えているサイン — 削る。それでも長いときだけ、
本文をプレーンテキストで出して**ターンを終え**、次のターンで聞く。

`AskUserQuestion`（1回の呼び出しに2問）:

- **Q1「この内容で投げていいか」** — このまま投げる / 直したい（Other で修正点）
- **Q2「どこまでやってもらうか」** — **起票だけ**（ボードに積む） / **起票して即着手**
  （hub が worktree を切って別タブに worker を立てる）

Q2 の答えを本文の末尾に「## 依頼範囲」として足す。**ここで聞いておくのが肝心**で、hub のタブに
人がいるとは限らない。hub 側でこれを聞くと、ユーザーがそのタブに来るまで報告が止まる。

**この行を落とすと「起票だけ」に落ちる**（hub の既定。勝手に着手はしない）。即着手してほしい
依頼で書き忘れると、起票されて終わる。

### 4. 渡す

`adjutant_send` を1回呼ぶ。

| 引数 | 中身 |
| --- | --- |
| `body` | §2 の本文 |
| `subject` | 結論の1文。人が一覧で見るのはこの行だけ |
| `from` | いまのセッション名（無ければ worktree 名） |
| `kind` | `report` |

`subject` の例:

```
検索結果の画像が縦に潰れる（ALPHA-957 の作業中に発見・起票して即着手を希望）
```

**宛先を書かない。** 引数に宛先が無いのは仕様で、いまいるリポジトリの hub に届く。別リポジトリの
不具合なら、そのリポジトリのチェックアウトから報告する（`repo` 引数で他所の hub へ投げることは
できるが、hub は自分のチェックアウトしか読めないので、ほぼ役に立たない）。

**hub が起動していなくても失敗しない。** 届け先は hub の受信箱ディレクトリで、hub は起動時と
待機に戻る前にそこを読む。hub が起動していれば、そのうえで一声かけて起こしにいく
（何で起こすかは設定が持っている）。返ってくる `present` / `woken` が:

- `present: true, woken: true` → 起動中の hub を起こした。そのまま処理される。
- `present: true, woken: false` → 受信箱には入った。hub が次に受信箱を見たときに読まれる。
- `present: false` → 書き置きになった。ユーザーに「hub が起動していないので書き置きした。急ぐなら
  `adjutant hub` で立ててほしいのだ」と伝える。立てるのを手伝うなら
  `adjutant spawn --cwd '{toplevel}' --title 'hub 起動' -- adjutant hub`
  （`{toplevel}` は Context の絶対パス。**省かない** — 新しいタブの cwd はターミナルの
  プロファイル次第で、git リポジトリの外だと即エラーになる）。

**相手の状態を見て送るのをやめる、という判断はしない。** 届け先はファイルなので、hub が
質問待ちでも取り込み中でも取りこぼしはない。送ってから知らせるのが正しい順序。

### 5. 自分の作業に戻る

送ったらこのコマンドは終わり。hub の返事は後から届くので、届いたら**issue 番号を1行メモして
元のタスクに戻る**。返信は要らない。そこから起票内容の議論に脱線しない — それは hub と
ユーザーの仕事。

**例外はひとつだけ: 1行目が `[質問]` で始まる返事。** これは hub が起票に足りない情報を聞いている
ので、**1往復だけ答える**。hub は別のブランチを見ていて、いまの worktree のコードを読めない —
読めるのは自分だけ。file:line を確かめて短く返し、それで終わりにする（議論はしない）。返すのも
`adjutant_send` で、`kind` は `answer`、`subject` の頭に元の質問の識別子を置く。

`[ack]` で始まる返事は「受け取った」の通知なので、何も返さない。

## 禁止

- **自分の権限で拒否された操作を hub に代行させない**（permission laundering）。拒否されたことは
  ユーザーに上げる。
- hub の返事を待つためのポーリング・`sleep` ループ。
