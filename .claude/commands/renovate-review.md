<role>
You are a senior Rust engineer analyzing dependency-update PRs created by Renovate.
Your job is to investigate the impact of the version changes, check where the code base is affected,
determine whether any CI failures are caused by the update, and then post a review with a merge
verdict as a PR comment.
</role>

## Target

Argument: $ARGUMENTS
- Accept the **URL** of the Renovate PR (e.g. `https://github.com/syarihu/agent-adjutant/pull/1234`) or a **PR number**.
- If it is empty, ask the user for the target PR URL or PR number.
- Extract **owner/repo** and the **PR number** from the URL. If only a PR number is given, treat the current repository (`syarihu/agent-adjutant`) as owner/repo.
- The URL must have the form `https://github.com/<owner>/<repo>/pull/<digits>` and a bare PR number must be digits only. If the argument is anything else, stop and ask the user; never write an unchecked argument into a shell command.
- Use the extracted owner/repo and PR number in all subsequent steps. Pass `--repo <owner>/<repo>` explicitly to `gh pr` commands.
  `gh api` does not accept a `--repo` flag, so include owner/repo in the endpoint path like `repos/<owner>/<repo>/...`.
- **This command must be run from a local checkout of the target repository.** Step 3's code-base search and `cargo tree` operate on the current working tree, so if the extracted owner/repo does not match the repository you are currently in, the impact analysis would be run against the wrong code. Before proceeding, confirm that the current working tree corresponds to `<owner>/<repo>` (e.g. compare `gh repo view --json nameWithOwner --jq .nameWithOwner` with the extracted owner/repo); if it does not match, stop and ask the user to run the command from the target repository's checkout.

**Important: write all comments and the review in English.** Technical terms such as crate names, version numbers, and file paths may stay as-is, but all explanations, descriptions, and recommendations must be in English.

## What Renovate updates in this repository

Renovate (`renovate.json`) opens three kinds of PRs here. Identify which kind each updated dependency is, because Steps 1–3 differ per kind:

1. **Rust crates** (`Cargo.toml` / `Cargo.lock`). Branches ending in `-lockfile` (e.g. `renovate/clap-4.x-lockfile`) change only `Cargo.lock`: the requirement in `Cargo.toml` (such as `clap = "4"`) already allows the new version. One update often moves several packages at once — a crate and its sub-crates released together (`clap`, `clap_builder`, `clap_derive`), and transitive dependencies pulled along with it.
2. **GitHub Actions** in `.github/workflows/`. Actions are pinned to a commit SHA with the version in a trailing comment (`uses: owner/action@<sha> # v2.9.2`). Renovate updates the SHA and the comment together, or only the SHA (a "digest" update) for actions that track a moving tag such as `# v1`.
3. **Vendored xterm.js packages** (`@xterm/*`, the group "xterm vendored packages"). A regex custom manager reads the versions from the table in `src/ui/vendor/xterm/README.md`. The actual files (`src/ui/vendor/xterm/*.js`, `xterm.css`, `LICENSE*`) are embedded in the binary with `include_str!` (`src/transport/board_http/assets.rs`), and **Renovate does not touch them**: it only edits the version column of the README table.

## Step 0: Find or clean up previous review comments

To avoid duplicates, find any existing auto-generated comment to edit in place, and delete extras if there are multiple.

1. Fetch **all pages** of the comment list for the target PR with `gh api --paginate "repos/<owner>/<repo>/issues/<PR number>/comments?per_page=100" --jq '.[] | select(.body | contains("<!-- renovate-review:generated -->")) | .id'` (one matching comment id per line; `--jq` runs per page, so the pages do not come back as separate JSON arrays). Always add `--paginate` so you do not miss comments on PRs with many comments.
2. To target only comments auto-generated by this command, look for comments whose **body contains the marker `<!-- renovate-review:generated -->`** (embedded at the end of the Step 4 template). This marker only appears in auto-generated comments, so a comment a human wrote by reusing the heading or template will not be modified or deleted by mistake.
3. From the matching comments, **keep the last one** (highest `id`) for in-place editing. Remember its `id` as `REVIEW_COMMENT_ID` (keep the number itself; shell variables do not survive between Bash calls, so later steps write the number into the command). If there are multiple matching comments, delete all **except** the one you saved with `gh api -X DELETE repos/<owner>/<repo>/issues/comments/<comment ID>`, one command per comment. If a deletion fails (the comment is already gone, or permission is missing), note it and carry on; it must not stop the rest of the process.
4. If no matching comment was found, set `REVIEW_COMMENT_ID` to empty.

## Step 1: Extract the dependency changes

- Read the PR diff (`gh pr diff <PR number> --repo <owner>/<repo>`) and identify which dependencies changed and how (old -> new).
- **Rust crates**: read the `[[package]]` entries in the `Cargo.lock` diff (`name`, `version`) and any requirement change in `Cargo.toml`.
    - Group packages that belong to one release (e.g. `clap` / `clap_builder` / `clap_derive`) under the crate Renovate named in the PR title, but still list each package's old -> new version.
    - For every package that is **not** a direct dependency in `Cargo.toml`, find which direct dependency pulls it in with `cargo tree -i <package> --edges normal,build,dev` (add `--target all` so platform-specific dependencies such as `libc` under `[target.'cfg(unix)'.dependencies]` are included; when the lockfile holds two versions of the package, name one as `<package>@<version>`). `cargo tree` reads the `Cargo.lock` of the local checkout, not the PR's, so pass the **old** version (or the bare name) — the new version is not in the local lockfile. Do not check out the PR branch for this. Packages added to or removed from `Cargo.lock` are changes too; list them. An added package is not in the local lockfile at all: find what pulls it in from the PR's own `Cargo.lock` (`gh api -H 'Accept: application/vnd.github.raw' 'repos/<owner>/<repo>/contents/Cargo.lock?ref=<head SHA>'`, then the `[[package]]` entries whose `dependencies` list it).
    - Note whether each direct dependency is a normal, build, or dev dependency (`[dev-dependencies]` only affect tests).
- **GitHub Actions**: list each changed `uses:` line with the old and new SHA and version comment, and the workflow file(s) it is in.
- **xterm packages**: list each changed row of the README table (package, old -> new version).
- List all updated dependencies together with their old and new versions.

## Step 1.5: Check CI failures and fetch failure logs

If the PR's CI is failing, you will analyze in a later step whether the failure is caused by the update. Here you only do **status checking and fetching/extracting the failure logs** (the causal analysis is done in Step 3).

> What you hit here is the **repository that hosts the target PR** (`<owner>/<repo>`), which is a separate axis from Step 2's `<libOwner>/<libRepo>` (the dependency itself). Do not confuse them.

1. Check the CI status. Run `gh pr checks <PR number> --repo <owner>/<repo>`.
    - If there are no failing checks, skip this step and go to Step 2 (omit the "CI failure cause and remediation" section from the review).
    - `gh pr checks` returns **exit code 8 when checks are pending or in progress**. In that case treat it as "not determined because CI is still running" and skip log fetching.
2. Get the **run ID and job ID** of the failing job. Since `gh pr checks` output has no job ID, get it from the check-runs API. **Note: the check-run `id` is not necessarily the GitHub Actions job ID**, so do not use it directly — parse the `run_id` and `job_id` out of the `html_url` (`/actions/runs/<run_id>/job/<job_id>`) instead:
    ```bash
    gh pr view <PR number> --repo <owner>/<repo> --json headRefOid --jq .headRefOid
    # then, with the printed SHA written in:
    gh api --paginate "repos/<owner>/<repo>/commits/<head SHA>/check-runs?per_page=100" \
      --jq '.check_runs[]
            | select((.conclusion|IN("failure","timed_out","cancelled","startup_failure","action_required")) and (.html_url|contains("/actions/runs/")))
            | (.html_url | capture("/actions/runs/(?<run_id>[0-9]+)/job/(?<job_id>[0-9]+)")) + {name, html_url}'
    ```
    - This project's CI runs on GitHub Actions. `.github/workflows/ci.yml` has one job, `check`, which runs `make check` (the layering and move-only scripts, `node --check` and `node --test` for `src/ui`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test` through `./scripts/check-test-leaks.sh`). The `move-only` job in `.github/workflows/move-only.yml` runs only on PRs labelled `move-only` (it shows as skipped otherwise). If a non-Actions check happens to be mixed in, `gh run view` cannot fetch it, so treat it as "logs not fetched / needs manual review" and do not assert a cause.
    - If there are many failing Actions jobs, you may **narrow to the main failing jobs** so the number of log fetches does not explode (one representative is enough for derived jobs with the same cause). If you narrow, note that in the review.
3. For each failing job, **save the log to a temporary file** (do not load the full huge log into context as-is):
    ```bash
    gh run view <run_id> --log-failed --job=<job_id> --repo <owner>/<repo> > <temp file>
    ```
    (Pass the `run_id` explicitly so resolving the job is unambiguous across `gh` versions. Logs can exceed hundreds of lines / 100KB.)
4. From the saved log, use the **Grep tool** to extract only the actionable lines (do not read the whole thing). Signatures to prioritize:
    - compiler and clippy errors: `error[E` (e.g. `error[E0599]: no method named ...`), `error:` and the `-->` line that follows with the file and line
    - clippy lints promoted by `-D warnings`: `error: ` followed by `= note: \`-D clippy::...\`` or `#[deny(...)]`
    - test failures: `test result: FAILED`, `---- <test name> stdout ----`, `panicked at`, `failures:`
    - formatting: `Diff in` (from `cargo fmt --check`)
    - `make: *** [...] Error`, `##[error]`, and `node:` / `AssertionError` from the `src/ui` checks
    - Only if the extraction still lacks information, read the surrounding area partially with Read.

## Step 2: Investigate release notes and changelogs

For each updated dependency:

> **Important — beware of mixing up repositories**: what you hit here is the **dependency's own repository**, denoted `<libOwner>/<libRepo>`.
> This is a **different thing** from Step 0/1's `<owner>/<repo>` (= the repository that hosts the target PR). If you confuse them, you will
> look at this repository's releases and get a 404. Identify `<libOwner>/<libRepo>` per kind:
> - **Rust crate**: the `repository` field from crates.io (`https://crates.io/api/v1/crates/<crate>`, via WebFetch), e.g. `clap` -> `clap-rs/clap`, `serde_json` -> `serde-rs/json`, `libc` -> `rust-lang/libc`. Several crates often share one repository (a workspace).
> - **GitHub Action**: the `owner/action` in the `uses:` line itself.
> - **xterm package**: `xtermjs/xterm.js` (the addons are released from the same repository).

1. Choose how to fetch the release-note body:
    - **When the dependency is hosted on GitHub, fetch the body directly as a primary source with `gh api`**.
      Get the release bodies with `gh api repos/<libOwner>/<libRepo>/releases/tags/<tag> --jq '{name, published_at, body}'` and summarize based on that `body`.
      Web search + WebFetch can mix guesses (wrong dates, non-existent changes) into the summary, so prefer the primary source from `gh api`.
    - **Many Rust crates publish no GitHub releases, or only a stub, and keep the real history in `CHANGELOG.md`** (sometimes per crate in a workspace, e.g. `clap_builder/CHANGELOG.md`). Read it with `gh api -H 'Accept: application/vnd.github.raw' 'repos/<libOwner>/<libRepo>/contents/<path>?ref=<tag>'` (or the default branch if the tag is not found) and take the sections for the versions in range.
    - If neither exists, compare the tags (`gh api repos/<libOwner>/<libRepo>/compare/<old tag>...<new tag> --jq '.commits[].commit.message'`) and say in the review that there is no changelog and the summary is from commit messages.
    - Only when the dependency is not on GitHub, or `gh api` cannot fetch it, use **web search / WebFetch** to find the official release notes or changelog. In that case do not take the content at face value, and back it up with a primary source when possible.
2. **Do not stop at a thin release body — follow it to the real content.** When a release body is only highlights plus a link ("see CHANGELOG.md", "full changelog"), with no explicit breaking-changes section, fetch the linked changelog or compare view and summarize from there instead of the stub.
3. **Check what Rust-specific requirements changed**, because they break builds without any API change:
    - **MSRV** (`rust-version` in the crate's `Cargo.toml` at the new tag). This repository builds with the latest stable toolchain (`dtolnay/rust-toolchain` with `toolchain: stable`) and declares no `rust-version`, so an MSRV bump only matters if it goes beyond the current stable; note it anyway.
    - **Edition** and **feature flags**: a renamed, removed, or newly default feature. Compare with the features this repository enables in `Cargo.toml` (e.g. `clap` with `derive`, `serde` with `derive`).
    - **Yanked versions**: check that the new version is not yanked (`https://crates.io/api/v1/crates/<crate>/<version>`).
4. **For GitHub Actions**, also check:
    - that the new SHA is the commit the version comment names: `gh api repos/<libOwner>/<libRepo>/commits/<tag> --jq .sha` should equal the SHA in the diff. For a digest-only update of a moving tag (`# v1`), say which commit the tag moved to and summarize the commits in between (`compare/<old sha>...<new sha>`).
    - changes to the action's inputs, outputs, default values, and the Node.js runtime it runs on (`runs.using` in `action.yml`), compared with the `with:` inputs this repository passes.
5. **For xterm packages**, read the releases of `xtermjs/xterm.js` for every version in range and check breaking changes in the APIs the board uses (search `src/ui` for `Terminal`, `FitAddon`, `Unicode11Addon` and the options and methods called on them). Check that the addon versions in the PR still go with the `@xterm/xterm` version (step 1 of "Updating" in `src/ui/vendor/xterm/README.md`).
6. **When the update spans multiple minor/major versions, cover the whole range, not just the two endpoints.** For a jump like `1.2.0 -> 1.5.1`, breaking changes may have been introduced in an intermediate release (`1.3.0`, `1.4.0`). Enumerate the intermediate versions and read each one's notes so nothing in between is skipped. For a `0.x` crate, a minor bump (`0.2` -> `0.3`) is a breaking release under Cargo's semver rules; treat it like a major one.
7. Based on all the sources gathered above, summarize the important changes. Pay particular attention to:
    - Breaking changes
    - Deprecated APIs / features
    - New features / behavior changes
    - Security fixes (also check the RustSec advisory database, https://rustsec.org/ , for the crate)
    - Bug fixes
   Anchor the **Breaking changes** and **Deprecations** you report to an explicit breaking-changes/deprecations section or changelog entry, not to a highlights blurb.
8. If migration steps are required, note them clearly.
9. **Do not guess the release-note URL you put in the review — always confirm it exists.** For a GitHub release,
   confirm that `gh api repos/<libOwner>/<libRepo>/releases/tags/<tag>` returns 200 (a 404 means the tag name is wrong).
   Tag naming differs per project and, in a workspace, per crate (`4.6.7` / `v4.6.7` / `clap_derive-v4.6.7`, etc.), so after building a URL from the version number, always verify it exists before writing it. For a changelog, link the file at the tag (`https://github.com/<libOwner>/<libRepo>/blob/<tag>/CHANGELOG.md`). If you cannot confirm a URL, fall back to the release list or the crate's page (`https://crates.io/crates/<crate>/<version>`) and state that explicitly.

## Step 3: Analyze the impact on the code base

For each updated dependency:

1. **Search the code base** for where the dependency is used.
    - **Rust crate**: `use <crate>::` and `<crate>::` paths, derive and attribute macros (`#[derive(Parser)]`, `#[command(...)]`, `#[arg(...)]` for `clap`; `#[derive(Serialize, Deserialize)]` and `#[serde(...)]` for `serde`), and `extern crate` if any. Crate names with `-` are written with `_` in code. A transitive dependency is not used directly; assess it through the direct dependency found in Step 1.
    - **GitHub Action**: every workflow that uses it, and the `with:` inputs passed. `.github/workflows/release.yml` runs only on a `v*` tag push, so an action used only there (or a change in how it is used there) is **not exercised by the PR's CI**; say so in the review.
    - **xterm package**: `src/ui` (the board terminal) and `src/transport/board_http/assets.rs`.
2. Check whether the breaking changes / deprecated APIs identified in Step 2 are used in the project.
3. **For xterm packages, the PR is incomplete by construction.** Renovate only changes the version in the README table, so the vendored files are still the old version and the table no longer matches them (nor the tarball hashes in the same row). Check the diff: if `src/ui/vendor/xterm/*.js` / `xterm.css` / `LICENSE*` and the sha256 column did not change, the impact is **High** and the required action is to vendor the new files by the "Updating" steps in `src/ui/vendor/xterm/README.md` (download and check each tarball, copy the files without the `sourceMappingURL` line, update the hashes, run `cargo test`, open a terminal from a board) on the PR branch before merging. Merging the PR as it is would leave the README claiming versions that are not shipped.
4. **Causal analysis of CI failures** (only if you fetched failure logs in Step 1.5). Cross-reference the extracted error content with the updated dependencies / breaking changes from Step 1/2 and the usage sites from Step 3-1, and determine whether it is caused by the update. **To avoid misattribution, always follow these rules**:
    - Assert "caused by the update" **only when** the file paths, symbols, crate names, and lint names in the error log **actually correspond** to an updated dependency or breaking change. If they do not correspond, do not assert it.
    - **Do not infer the failure type from the job name or the step name** (the single `check` job runs everything in `make check`, so read which command in the log actually failed).
    - **A new stable Rust can fail CI on its own.** CI uses `toolchain: stable`, so a lint added or tightened in a new Clippy, or a newly deprecated std API, fails `cargo clippy ... -D warnings` regardless of the update. Before blaming the update for a clippy or compiler warning, check whether the latest CI run on the base branch fails the same way (`gh run list --repo <owner>/<repo> --branch main --workflow ci.yml --limit 5`) and whether the reported lint is new in the current stable.
    - Do not mistake other **unrelated noise** — flaky tests, infrastructure/network outages, cache inconsistencies (`Swatinem/rust-cache`), Node.js deprecation warnings from actions — for the cause. When in doubt, consider whether the base branch also fails or whether a re-run fixes it.
    - State the causal confidence in the review as one of three levels: **Certain / Possible / Likely unrelated**.
5. Determine the impact level:
    - **Low**: No breaking changes. Only bug fixes or minor improvements. No code changes needed.
    - **Medium**: A deprecated API is used, or a behavior change could affect the project. Code changes may be needed but not urgent.
    - **High**: A breaking change directly affects the project, or the PR cannot be merged as it is (the xterm case in Step 3-3). Code changes are required before/after merge.
    - **Handling CI failures**: escalate to "High" **only for CI failures confirmed to be caused by the update**. For unrelated (or undeterminable) CI failures, do not raise the impact level; instead just note "there is an unrelated/undetermined failure in CI (needs manual review)" in the review.

## Step 4: Post the review as a PR comment

Create a single PR comment with the structure below. Write the review body to a temporary file with the **Write tool first** (e.g. under a scratchpad), then post or update it:

- **If `REVIEW_COMMENT_ID` is set** (existing comment found in Step 0): edit it in place with a PATCH request. `-F body=@<file>` makes `gh` read the field's value from the file:
  ```bash
  gh api -X PATCH "repos/<owner>/<repo>/issues/comments/<REVIEW_COMMENT_ID>" -F body=@<temp file>
  ```
- **If `REVIEW_COMMENT_ID` is empty** (no existing comment): create a new comment.
  ```bash
  gh pr comment <PR number> --repo <owner>/<repo> --body-file <temp file>
  ```

(Passing the body directly to `--body` tends to break line breaks and markdown, so always go through a file.)

```markdown
## Dependency Update Review

### Summary

- **Overall impact**: [Low / Medium / High]
- **Merge verdict**: [Safe to merge / Merge with caution / Code changes required]

### Dependency changes

#### [dependency-name] (old-version -> new-version)

- **Kind**: [Rust crate (direct / transitive via <crate>, normal / dev) / GitHub Action / vendored xterm package]
- **Impact**: [Low / Medium / High]
- **Key changes**:
    - [summary of important changes]
- **Breaking changes**: [None / list of breaking changes]
- **Affected code**:
    - [list of affected files and usage sites, or "None"]
- **Required action**: [None / description of required changes]
- **Release notes**: [link to the release notes or changelog]

(repeat per dependency; packages released together, such as a crate and its sub-crates, may share one entry that lists each package's versions)

### CI failure cause and remediation

<!-- Include this section only if CI is failing. If there are no failures, omit it entirely. -->

- **Failed checks**: [job name and link to the failing job]
- **Error summary**: [actionable errors extracted from the log (compiler errors, clippy lints, test failures, etc.)]
- **Confidence it is caused by the update**: [Certain / Possible / Likely unrelated]
- **Cause analysis**: [which change in which dependency causes this error, or the basis for judging it is not caused by the update]
- **Required action**: [remediation plan, or "unrelated to the update, needs manual review"]

### Overall assessment

[Detailed assessment of whether this PR is safe to merge, plus any caveats or follow-ups needed]

---

> 🤖 This comment was auto-generated by the `/renovate-review` command.

<!-- renovate-review:generated -->
```

- **Always append**, exactly as in the template above, the note that the review was auto-generated by the `/renovate-review` command and the marker `<!-- renovate-review:generated -->`.
  The marker is an HTML comment, so it is not shown on GitHub and is used for the deletion-target check in Step 0 (so only comments generated by this command can be safely identified).

## Guidelines

- Keep the analysis thorough but concise.
- Always include links to the release notes or changelog.
- If the release notes cannot be found, state that explicitly.
- Focus on the actual impact rather than enumerating every minor change.
- When unsure about the impact level, err on the safe side (the higher impact level).
- Keep the summary's "Merge verdict" consistent with the overall impact: **Low -> Safe to merge** / **Medium -> Merge with caution** / **High -> Code changes required**.
- A lockfile-only update within the semver range declared in `Cargo.toml` is expected to be compatible, but do not assume it: crates sometimes ship behavior changes or MSRV bumps in patch releases. Base the verdict on what Step 2 found.
- **Do not overstate a deprecation's removal timeline.** A "deprecated" API is not automatically "removed in the next major". Only state a
  concrete removal version if the release notes or changelog explicitly say so. If the source only says
  "deprecated" without a removal version, write it as "deprecated (removal timeline unconfirmed — verify before the next major upgrade)"
  rather than asserting when it breaks.
- When referencing an external project's Issue or PR, always use the full URL rather than a shorthand like `#number`
  (e.g. `https://github.com/<libOwner>/<libRepo>/issues/1234`), because the shorthand would be mistakenly linked as an Issue/PR
  of this repository.
- **Never emit live GitHub @mentions in the comment.** Release notes and changelogs often contain contributor handles like
  `@someuser`, and pasting them verbatim into a PR comment sends real notifications to those people (this is a public repository, so the
  pings actually reach them). Whenever you would write an `@handle`, neutralize it so it does not auto-link — wrap it in inline
  code (`` `@someuser` ``) or drop the leading `@` (e.g. `someuser`). Apply this to every username taken from release notes,
  changelogs, commit authors, or "thanks to ..." credits. The same applies to team mentions like `@org/team`.
- **Always put a space before and after a URL.** If a full-width parenthesis or text follows a URL directly, the auto-link swallows it
  and the link breaks (e.g. `...v4.6.7(the corresponding tag...` is bad -> put a space after the URL like `...v4.6.7 (the corresponding tag...`).
